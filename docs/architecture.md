# Архитектура — этапы 0 и 1

Next.js App Router + React, TypeScript strict. UI: app/page.tsx, responsive shell и формы. Domain: lib/profile.ts (Zod). Data: lib/supabase.ts (Supabase JS SDK). Точные версии зафиксированы package.json и package-lock.json. CSS использует дизайн-токены; системная, светлая и тёмная темы. Без Tailwind/shadcn на этом этапе: минимальная зависимость, семантические формы.

Клиент использует только публичный publishable/anon key и пользовательский JWT. Данные защищает PostgreSQL RLS, а не визуальное скрытие страницы. До сессии профиль не запрашивается. Нет сервисного ключа, фальшивого backend или синхронизации через localStorage. Профиль сохраняется с проверкой version; 0 обновлённых строк означает конфликт, UI сохраняет правки на экране и просит загрузить актуальную версию. Ошибки показываются явно.

Ранее созданная статическая версия сохранена в legacy/ и исходных файлах; её данные localStorage не удаляются. Next.js не публикует эти файлы автоматически. Импорт задач будет отдельным действием на этапе 2.

Netlify: статический экспорт Next.js, build `npm run build`, publish `out`, base пусто. После сборки Python-сервер раздаёт папку out. Внешний Supabase подключается владельцем проекта. Публичные переменные встраиваются в клиент на этапе сборки; после изменения нужен новый deploy.

## Этап 2

`components/planner.tsx` — UI недели/дня, задачи, события и формы. `lib/planner.ts` — типы, Zod, Temporal и чистые функции дат/интервалов; `lib/planner-data.ts` — только Supabase-запросы и обработка ошибок. Данные загружаются с пагинацией по 500 строк, чтобы не обрезать шаблоны на стандартном лимите PostgREST. Экземпляры читаются для недели с запасом для различных часовых поясов и перехода через полночь.

RPC создания/редактирования атомарно меняют шаблон и экземпляр с проверкой обеих версий. Экземпляры повтора материализуются лениво и имеют постоянный source_date, отдельный от редактируемой local_date. Хранимые моменты времени — timestamptz, локальные даты — date. Temporal reject и серверный helper не выбирают молча одну сторону DST-fold.

PGlite проверяет SQL и RLS без внешней базы. Playwright-стенд использует локальный SQL и тестовый auth API; браузерная проверка hosted Supabase Auth остаётся отдельной. Подробные ограничения — docs/stage-2.md.
