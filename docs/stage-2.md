# Этап 2: задачи, календарь, день

## Реализовано

- Сегодня: выбранная дата, текущий/следующий временной блок, лента дня, обязательный план/факт, ближайшие дедлайны и предупреждения пересечений.
- Календарь: день / неделя, переходы по неделям, выбор даты; Задачи: список выбранной недели с поиском, категорией и статусом.
- Создание задач без времени или с временным блоком, название/описание, категория, приоритет, длительность, необязательность, подтверждённый/предварительный/неизвестный срок. Срок может быть только датой, без выдуманного часа.
- События с фактическими началом/окончанием, в том числе через полночь; закреплённые события требуют явного подтверждения изменения и архивирования, проверяемого также серверной RPC.
- Редактирование и перенос отдельного повторения, статусы «запланировано/частично/готово/пропущено», отмена выполнения, фактические минуты и заметки. Плановые минуты не выдаются за фактические.
- Повторения: ежедневно или еженедельно, с явно заданным сроком до года. Повторения создаются идемпотентно для просматриваемой недели. Перенос экземпляра сохраняет source_date и не порождает дубликат на старой дате.
- Архивирование/восстановление всей задачи или серии вместо необратимого удаления. Редактирование общих свойств влияет на всю серию, дата/время/статус — на экземпляр. Изменение расписания всей серии пока выполняется архивированием старой и созданием новой.
- Запись только после успешной операции базы. Ошибки сохраняют форму. Версии шаблона и экземпляра проверяются атомарно; конфликт не затирает свежие данные.
- Обновление при возвращении в окно, ручное обновление и перезагрузка. Это не Realtime и не офлайн-синхронизация.
- Дата выбранного дня сохраняется в URL вкладки. Часовой пояс профиля используется для отображения; часовой пояс существующей записи — для её редактирования. Переходы DST проверяются отдельно.

## Модель и безопасность

Миграция `supabase/migrations/202610260002_planner.sql` добавляет tasks, task_occurrences, calendar_events, event_occurrences, индексы, RLS SELECT и ограниченные RPC мутаций. Все четыре таблицы закрыты для anon. Direct INSERT/UPDATE/DELETE для authenticated запрещены. SECURITY DEFINER RPC фиксируют search_path, проверяют auth.uid(), владельца и ожидаемые версии. Составные FK исключают связи между владельцами. CHECK-ограничения запрещают невозможные длительности, отрицательный факт, неизвестные enum и некорректные сроки. Персональных seed-данных нет.

Миграцию можно выполнять повторно. Она не удаляет профиль или предыдущие данные и не отключает существующий RLS.

## Проверки и ограничения

- `npm test`: domain-тесты и реальный PostgreSQL в WASM (PGlite), две роли/два пользователя, RLS, отказ чужих RPC, атомарный откат, CRUD статусов, версии, повторы, архив, фиксированные события, DST; плюс ранее существовавшие тесты.
- `npm run test:e2e`: Chromium + локальный Next.js + настоящий SQL. Только auth-транспорт подменён контролируемым локальным стендом; стенд не входит в production bundle. Проверяются задачи, перенос/перезагрузка/статусы, события, конфликты, два устройства, отказ устаревшей записи, ошибка сохранения, отдельный пользователь, мобильная ширина, навигация и выход.
- Скриншоты E2E: test-results/planner-360.png и planner-desktop.png (игнорируются Git, только тестовые данные).
- `npm run typecheck`, `npm run format:check`, `npm run build` — обязательные локальные проверки. Отдельного ESLint пока нет; format:check не заменяет semantic lint.
- В настоящем Supabase миграцию применяет владелец проекта. Облачные CRUD/RLS и реальные два физических устройства требуют отдельной проверки; локальный стенд не доказывает работу hosted Supabase Auth.
- Невозможное/неоднозначное время повторения в зоне DST возвращает явную ошибку генерации; время не сдвигается молча. Для изменения времени всей серии архивируйте её и создайте заново с валидным временем.
- Пока нет drag-and-drop, месячной сетки, произвольного RRULE, автоматического распределения дня, языкового журнала, импорта старого localStorage или медицинских выводов. Следующий этап — языки и привычки (30+30).

## Обновление сайта

1. Supabase → SQL Editor → выполнить целиком `202610260002_planner.sql` (миграция профиля уже выполнена).
2. Netlify публикует branch feature/cloud-foundation с `npm run build` → `out`, как задано netlify.toml. Переменные Supabase остаются прежними.
3. После Published обновить сайт; создать задачу, обновить страницу, перенести её, отметить частично/готово/отменить; повторить на другом устройстве.
4. Без второй миграции UI показывает инструкцию, а не притворяется сохранением. Настройки профиля продолжают работать.
